# Agent Lord

Manage multiple related or independent tasks from one scheduling session, with one logical task per durable endpoint. Treat `node core/dist/cli.js` as the control plane: the model supplies intent and performs Codex App host-tool actions when requested, while the script owns provider defaults, validation, retries, state, recovery, and artifact extraction.

For explanations and reports addressed to the user, read and apply the installed `explain-as-fool` Skill under the [dependency contract](#skill-dependencies). Include its resolved readable path in the prompt of any endpoint writing that material, including later turns. Pipeline-specific review and plan standards are named at their point of use.

## Skill dependencies

Agent Lord depends on three Skills maintained in [dev-skills](https://github.com/coder-xieshijie/dev-skills). Install them before use following the [quick start](README.md#2-install-the-required-skills). Agent Lord owns scheduling and pipeline stages; dev-skills owns the shared content standards. This repository does not maintain copies of those standards.

| Skill             | Apply when                                                           | Default installed entry                     |
| ----------------- | -------------------------------------------------------------------- | ------------------------------------------- |
| `review-rules`    | Reviewing findings, proposed fixes, cross-exams, and checker results | `~/.agents/skills/review-rules/SKILL.md`    |
| `plan-for-agents` | Writing or checking a plan's content and completeness                | `~/.agents/skills/plan-for-agents/SKILL.md` |
| `explain-as-fool` | Writing explanations and reports for the user                        | `~/.agents/skills/explain-as-fool/SKILL.md` |

Before the affected assignment, resolve each required Skill from an explicit user-provided location, the host's registered Skill path, or the default entry above, following symlinks to absolute paths. The execution endpoint itself must be able to read the Skill and its relative references; another machine or sandbox needs its own installation or a run-local snapshot that keeps the Skill's layout.

Pass the absolute paths, required reading, and scope in the prompt: naming a Skill does not load it, and the runtime neither discovers nor installs dependencies. Applying a Skill as a content standard does not invoke a separate workflow, add roles, or change its explicit-invocation setting. Record resolved paths and content hashes, with the dev-skills commit when available, in the run's input versions, and keep that content for later turns and replacement endpoints; if the installed source changes mid-run, use the recorded revision or snapshot instead of silently switching rules.

A missing or unreadable Skill or reference stops only the affected assignment until resolved; name both. Do not substitute a repository copy or install or update Skills during a task.

## Scheduling ownership

The user-facing Codex Desktop, Codex CLI, Claude Code, or MCode session explicitly assigned scheduling by the user is the sole Agent Lord scheduling caller. A user may give this role to a previously resumed execution session; that explicit assignment supersedes its earlier execution-only role for the new workflow. It directly dispatches every Agent Lord execution endpoint and owns user-level assignments, provider/model selection, continuation, recovery, supervision, artifact exchange, and pipeline progression. Do not delegate those Agent Lord responsibilities to a coordinator CLI.

Give each CLI the goal, necessary context, expected outcome, and boundaries required by the user, authorization, or shared-workspace coordination. The CLI owns its internal decomposition, implementation, tool choices, native subagents, and validation approach. Leave healthy execution alone; intervene when the user changes direction or verified failure calls for recovery. Caller preferences for algorithms, libraries, command sequences, output chunk sizes, or test counts are not task constraints unless the user requires them.

Carry the user's subagent instructions into every applicable task prompt, including later turns and handoffs, without weakening them. Permission leaves the choice to the CLI; a preference prioritizes suitable delegation and asks the CLI to briefly explain non-use; an explicit assignment requires the specified subagent work, with any user-specified subagent model or effort. These instructions govern native subagents within the assignment; they do not authorize additional Agent Lord endpoints.

Each dispatched CLI receives one concrete execution task, which may include implementation, analysis, review, testing, and authorized delivery. Include the following executor constraint in every caller-authored CLI prompt, including later turns and handoff packets; the executor need not load this Skill to receive it:

> Do not invoke Agent Lord, directly or through a subagent. Return requests for additional execution endpoints or scheduling workflow changes to the scheduling caller.

Native subagents are internal execution of the assigned task, not additional Agent Lord endpoints or caller-level workflow nodes. The assigned scope, source, and write constraints still apply. During supervision, native `task` / `Task` / `Agent` use alone is not a delegation violation and does not require the execution endpoint to repeat the work.

### Task context preparation

The scheduling caller authors the task prompt; the runtime delivers it without selecting or summarizing documents. Cover the following content as applicable, combining it for simple tasks rather than imposing five headings or empty sections:

- **Goal and continuation state:** what this endpoint takes over and why it matters (who uses the result, for what), verified completed work, remaining work, and where its assignment ends. Include history only when it affects this execution.
- **Current decisions and authorization:** confirmed user choices, scope, write/publication authority, and the concrete [subagent instructions](#scheduling-ownership). Distinguish user decisions from assistant proposals and unresolved questions.
- **Versions and input index:** relevant source/document versions and accessible paths, each material's purpose and authority, and required reading or the condition that triggers it. Distinguish the checkout to modify from any reference source revision; check source claims against the assigned revision.
- **Deliverables and completion criteria:** required outputs, publication steps, and what done means as observable outcomes plus the evidence to report. Distinguish delivered artifacts from working records.
- **Executor constraint:** include the [fixed constraint](#scheduling-ownership) without expanding it into general execution advice.

Prepare that content with these rules:

- Resolve superseded instructions using existing user decisions and identify the currently effective requirements. Label obsolete instructions in referenced history; preserve original evidence. Keep genuine unresolved conflicts explicit rather than inventing a decision or handing down contradictory commands as equally current.
- Reference applicable Skills and repository rules by accessible path and scope. Inline concrete task requirements, explicit overrides, and necessary content the endpoint cannot access; avoid copying general procedures already supplied by those references. Binding decisions must not be hidden behind optional reading.
- Preserve complete source documents; a caller summary never replaces a document the user or a named pipeline requires in full. Require complete reading only then; otherwise state each document's purpose and let the endpoint read what the task needs. Keep detailed evidence in referenced materials rather than duplicating it in the prompt.
- Write outcomes and reasons, not procedures. Leave reading order, method, and verification steps to the endpoint unless the user or a named pipeline requires them; add no generic re-check step, and pass the user's own verification instructions through unchanged.
- State only boundaries that prevent a real problem, once each, with the reason. Endpoints run unattended and take wording literally, so stacked prohibitions or emphatic phrasing make them stop early or over-apply a rule. Tell the endpoint to carry reversible in-scope work through without asking, finish whatever a question does not block, and return to the scheduling caller only decisions the user must make and destructive or irreversible actions.
- Leave out the endpoint's memory, remaining context, and who reads its final message. An endpoint told it has no memory or that its last message is a handoff tends to wrap up early instead of finishing.
- Deliver audit records when required by the user, a named pipeline, or an actual review/handoff need. Otherwise keep process notes in existing working records; a self-check alone does not require a new repository artifact or an additional reviewer or workflow stage.

Before dispatch, verify indexed files are readable from the endpoint's environment. Declare required files inside its workspace with repeatable `--require-input` on `start`, `turn`, or `request-add`: the runtime checks readability and non-zero size before launching and records path, bytes, and SHA-256 ([input preflight](references/protocol.md#declared-input-preflight)), which proves the file was supplied, not that it is complete. Check external files separately; when a path is inaccessible or a frozen snapshot is required, provide an accessible copy or the necessary inline content, and keep referenced inputs available for the duration of execution.

Later turns on the same endpoint may provide an explicit delta identifying what it changes in the existing task contract. Fresh endpoints and handoffs need enough current context to execute independently. In both cases preserve every still-applicable user requirement and include the executor constraint and applicable subagent instructions.

### Tasks added during execution

When the user steers the scheduling session, classify the instruction as a change to an existing task, a new related task, or a new independent task. Preserve existing tasks and their supervision unless the user explicitly cancels or replaces them.

- A new task gets a new `task_id` and is dispatched when its dependencies and workspace contract permit, even while earlier CLIs run. Keep unrelated goals in separate task sets or runs; for a related addition, update the affected run manifest, dependencies, and artifact exchange before dispatch.
- A change to an existing task continues its saved endpoint with `turn` after the current operation is terminal. Agent Lord has no in-flight steer: while the task runs, register the instruction in the [request inbox](references/supervision.md#passive-request-inbox) with `request-add` so it survives compaction or a restart, report it as pending, and `request-dispatch` it once the task is idle.
- After adding endpoints, include every active task in the next checkpoint selection exactly once under the [waiting rules](#waiting-and-reporting); `run-add` keeps a run-bound observer in sync.

## Runtime setup

Use Node.js 24 or newer. From this Skill's repository root, run `pnpm install --frozen-lockfile` and `pnpm --filter @agent-lord/core build` after installation or source updates. Invoke the compiled CLI from this root; when calling it elsewhere, use its absolute path. Provider binaries come from the terminal environment or the configured `AGENT_LORD_*_BIN` variables. Switching an existing Python installation follows the [migration guide](references/python-to-typescript.md).

## Invariants

- Use scripts, CLI and authenticated HTTP for dispatch, supervision and observer verification. Agent Lord must not invoke or depend on Computer Use, CUA or browser automation, including as a fallback. A supported host link-opening API is presentation only; visible-page confirmation is not a completion requirement.
- Keep the delegated task's implementation, analysis, review, test execution, and semantic acceptance in the user-authorized external endpoints unless the user explicitly asks the caller to take over in the current session. The scheduling caller handles context transfer, dispatch, supervision, and result convergence, and may directly inspect dispatch contracts, run records, and deliverable completeness or review the orchestration process itself. These control-plane checks do not authorize adding workflow nodes.
- Start only with explicit user authorization. Preserve user choices for target, source revision, model, effort, task scope, and external writes.
- Use `dangerously_bypass` for every new local CLI dispatch, including reviews and handoffs; omit `--read-only`. Express read-only review, no-code-change, and external-write restrictions in the task prompt. These semantic limits remain binding; they do not make the process read-only or expand authority for external writes.
- Treat the user-specified endpoint set as part of the execution contract. Dispatch every requested Codex CLI, Claude Code CLI, or MCode CLI endpoint exactly; never drop or substitute a named provider.
- Keep one endpoint per `task_id` and one in-flight operation per task; the dispatch lock and operation journal enforce this across processes, so add no caller-side lock. Prefer continuing the saved endpoint; when necessary, replace it under [endpoint replacement](#endpoint-replacement) without additional user confirmation.
- Operation-scoped workspace and branch write leases serialize local CLI tasks. Bypass processes, including reviews, are writable to the runtime and hold exclusive leases; concurrent tasks need separate worktrees and checkout branches. An unfenced writable operation keeps blocking new writers until `checkpoint` fences it.
- Store task, operation, action, event, log, and artifact state under `${AGENT_LORD_STATE_DIR:-$HOME/.codex/state/agent-lord}`, never in the target repository.
- Freeze the resolved model, effort, retry plan, permission posture, and source contract when the task starts; every later turn reapplies them.
- Use fixed full SHAs for revision-sensitive work. Review prompts require an unchanged checkout at the frozen head; verify that scope before accepting review artifacts. The runtime permits a writable repo-managed task to advance only on its contract checkout branch as a descendant of the last verified head, which becomes the new verification baseline. That capability does not authorize a review task to change its source.
- Exchange sanitized artifacts, not raw provider logs or reasoning traces.
- The user owns the workflow: its task set, dependencies, output boundaries, roles, order, and completion conditions, or a documented named pipeline. Preserve all of them and add no planner, reviewer, tester, audit, integrator, or other node that neither names; creating, retrying, or recovering an internal `task_id` grants no such authority. Each extra endpoint multiplies cost and loses context at its handoff, so report a concern to the user instead of extending the workflow.
- Before the first dispatch, decide whether named actions are independent: run confirmed-independent actions concurrently under a valid workspace contract and ask when independence is unclear. Do not serialize them because the user never said "parallel", or to avoid asking about an unauthorized integrator or merge order.

## Pipeline routing

- For every multi-endpoint or named pipeline, read [references/pipelines/common.md](references/pipelines/common.md) and freeze its run manifest, barriers, role checks, convergence bound, and final deliverable before dispatch.
- For `plan-cross-review`, or a request to cross-review and rewrite an existing complete plan, read [references/pipelines/plan-cross-review.md](references/pipelines/plan-cross-review.md). Execute two reviewers → a fresh checker that then writes the plan → a fresh independent verifier, with bounded revision. This specific route takes precedence over generic cross-review; it delivers a complete plan, not implementation code.
- Otherwise, when the request says “交叉 Review”, “交叉审查”, or `cross-review`, also read [references/pipelines/cross-review.md](references/pipelines/cross-review.md) and execute its MCode Opus 5 `xhigh` + Codex `gpt-6-astra` / `high` mutual-review → independent new-session MCode Opus 5 `xhigh` check policy. The phrase authorizes only the nodes documented there; explicit user overrides still win.
- When the request says `plan-to-implement`, or asks to turn an existing implementation plan into code, read [references/pipelines/plan-to-implement.md](references/pipelines/plan-to-implement.md) and execute one implementation session per plan stage on the delivery branch → a reviewer and an acceptance tester on the finished head. The phrase authorizes only the nodes documented there; explicit user overrides still win.

## Deterministic loop

Execution is decoupled from waiting: a new CLI dispatch returns a `RUNNING` receipt while a detached controller keeps executing; collect terminal state with `checkpoint`. A host wait timeout ends only the wait, never the execution.

1. Resolve the exact repository, source branch, and fixed head/base. Batch independent repository and provider-discovery reads; keep source resolution and dispatch in dependency order. Reuse skill instructions and command help already verified in this session while their source/version is unchanged; refresh mutable repository and provider facts needed for this dispatch. For an unknown MCode model identifier, query `mcode provider list --json` directly and retain only the relevant provider/model/variant fields. Leave delegated code investigation to the endpoint.
2. Author the task prompt using [task context preparation](#task-context-preparation). Record the user's exact request in a private `--invocation-file` JSON with `user_request` and `trigger: "user_request"`; caller-authored follow-ups use `trigger: "caller_followup"` and a short `reason`. Bind the scheduling client and its own Session identity under the [invocation metadata](references/protocol.md#invocation-metadata) contract (Claude Code and MCode supply an explicit `caller` or the `AGENT_LORD_CALLER_*` environment) and verify the returned `invocation.caller`; report unavailable identity instead of guessing it from the latest session. Keep input files outside the repository and remove caller-owned files in the result-retrieval batch.
3. Inspect `node core/dist/cli.js start --help` on first use or when the command surface is uncertain or has changed, then run `start` with every explicit user choice. For revision-sensitive local CLI work, use `--repo`, `--source-branch`, one explicit workspace policy, and `--head-sha`; the control plane freezes the resolved checkout as the target. Use `--target` when the exact working directory already is the contract. Do not recreate these preflight checks manually.
4. Before the first supervision wait, bind the observer once with `pnpm --dir <agent-lord-root>/observer preview:attach --run-id <run>` (or `--tasks` for an individual task), verify `binding_verified` and every requested task, and open the focused link once through the host API or return it to the user. A run subscription follows later members; reattach only for another run, a task-only selection change, or observer recovery. [Task binding](observer/README.md#task-binding-after-dispatch) covers reuse and failures. Skip it when the user asks for background execution without a page.
5. Pass `--include-response` to `start`, `turn`, `recover`, `handoff` and `accept` as well as `checkpoint`, so a successful return includes the final text. Process the returned envelope until terminal:
   - `ACTION_REQUIRED` (Codex App only): call exactly `action.tool` with `action.arguments`, save the raw result outside the repository, and pass it to `accept --action-id <id> --result-file <file>`; add `--auto-read` when the next step would only be another polling read. [The App transport](references/transports.md#codex-app-transport-seam) covers thread identity and route recovery.
   - `RUNNING`: supervise local CLI work with `checkpoint --include-response` waits that cover every active task managed by this caller, including independent runs, in exactly one selection each under the [waiting rules](#waiting-and-reporting). Use `check` for a needed full-state diagnosis of one established task, or to request the next Codex App read when `accept --auto-read` was not used. Only `checkpoint` supervises dead controllers; see [`check` versus `checkpoint`](references/supervision.md#check-versus-checkpoint).
   - `CHECKPOINT_ACTIONABLE`: process every ordinary envelope in `actionable`.
   - `SUCCEEDED`: consume the canonical `response.text`, artifact and execution evidence from the terminal envelope once. A text-only ending is a report, not proof of completion: when it lists unfinished in-scope work without a blocker, `turn` the same endpoint naming those items, at most twice per task. If the command returned no inline text, retrieve it with `check --task-id <id> --include-response`; do not repeat artifact or metadata reads. Inspect `delivery` separately before claiming the requested files or commit are complete. Clean up caller-owned inputs in that same batch; no terminal browser check or duplicate completion ledger is required.
   - `ERROR`: consume an offered `safe_recovery` when appropriate. `CONTINUE_SAME_SESSION` means run `recover --task-id <id> --operation-id <failed-id>`, then supervise the returned operation. A terminal `claude-cli` `RESULT_INVALID` is covered by the user-authorized [scripted retry](references/protocol.md#scripted-claude-result_invalid-retry): run `retry-invalid --task-id <id> --operation-id <failed-id>`, which continues the same session when it can and owns the budget, replacement trigger, and lineage. Otherwise evaluate [endpoint replacement](#endpoint-replacement), or report the structured error. An absent recovery action is not itself a permission request.
   - `NEEDS_DECISION`: resolve the named decision from existing authorization, including the replacement policy below; ask the user only for authority still missing. Preserve explicit model, source, scope, and permission choices.
6. Start a later round with `turn` only after the previous operation is terminal. Record its request source/reason with `--invocation-file`, then supervise using the existing observer binding. The script reapplies the saved execution contract and deduplicates an identical in-flight message. For concrete local CLI deliverables, declare requested non-empty workspace-relative files with `--require-file` on `start` or `turn`. Add `--require-commit` only when a Git commit is part of the authorized delivery, including named implementation pipelines that require it. These structural checks do not establish test results, UI quality, or semantic acceptance.

## Endpoint replacement

The scheduling caller may replace an agent after repeated failures, a lost or unusable session, exhausted context, or another concrete condition that makes continuation impractical. This is authorized recovery of the same assigned role and needs no additional user confirmation; record and briefly report the reason.

- Give the new agent a self-contained, sanitized handoff: objective and acceptance criteria; source/workspace and constraints; completed work and artifact paths; decisions already made; failures and attempted recovery; remaining work; and uncertain execution or delivery. Transfer only inputs permitted for that role, preserving review independence.
- Confirm the old operation has ended or is fenced before a replacement writes to its workspace. Reconcile uncertain side effects before replaying them; `DELIVERY_UNKNOWN` alone does not authorize duplicate execution.
- Use a fresh `task_id`, preserving the old binding, and dispatch it with `start` and the handoff as its prompt; an authorized replacement that must continue an exact dirty workspace uses the [legacy handoff command](references/protocol.md#legacy-handoff-command). Record old/new task and endpoint identities, `replacement_for`, reason, and context artifact in the run manifest or task recovery record outside the repository; in a provenance-bound run, register the replacement with `run-add --nodes-file` and pass `start --run-id`. Refresh supervision and observer selection after dispatch.
- Preserve provider, model, effort, source/workspace contract, permissions, task scope, and role unless a change is separately authorized. Recheck artifacts and role independence against the new identity, and disclose the new identity in pipeline checks. Replacement occupies the existing workflow node and retains its progress and retry/convergence bounds; where no bound exists, set a finite attempt bound before dispatch and stop with the unresolved work when it is exhausted. A new session never resets a `retry-invalid` budget, and that budget never extends a semantic round or convergence bound.

## Workspace and parallel-write policy

- Create task-required worktrees and their isolated local branches for any authorized task without additional user confirmation. Choose distinct temporary branch names when needed. This authorization covers isolation only; endpoint replacement follows its own policy above, while workflow expansion, external writes, and source exceptions require their own authority.
- `reuse-or-create`: reuse the one clean source-branch worktree or create it; writable operations hold exclusive workspace and branch leases until the provider operation ends.
- `isolated`: use a distinct explicit `--workspace-branch` for each concurrent CLI task, including bypass reviews; create or reuse its worktree from the fixed source head. Continue later rounds in that same task's workspace.
- `shared-readonly` and `--read-only` remain low-level compatibility capabilities; do not select them for new Skill dispatches. A strict review prompt cannot satisfy the runtime's read-only requirement for a shared lease.
- Concurrent writers on one MR need a caller-declared parallel group, worker order, and one integrator started only after the workers are terminal; read [declared same-MR parallel writes](references/protocol.md#declared-same-mr-parallel-writes) before dispatching them. Agent Lord validates that contract and never invents workers, an integrator, merge order, or another MR. Concurrent reviews use isolated worktrees without integration metadata.

## Waiting and reporting

For multi-endpoint work, register all authorized nodes, including pending ones, before dispatch with `run-create --nodes-file ...`, and start each with `--run-id ...`; each node records its role and the exact user request, named pipeline, or replacement it comes from, under [node provenance and reporting](references/scheduling-updates.md). A self-authored manifest is not authority. Add assignments with `run-add --nodes-file ...` and supervise with `checkpoint --run-id ... --include-response`. After receiving and processing each terminal result, acknowledge its receipt with `run-ack`; an acknowledgement means the caller received the result, not that its content passed review. Membership persists across caller restarts; the runtime neither dispatches tasks nor chooses their implementation.

A result in a run that stays unacknowledged for `control.result_alert_seconds` (default 30 minutes) makes the detached worker record a `result-unreceived` event and alert the user once: a Feishu direct message from the `lark-cli` app bot to the logged-in user, falling back to a macOS notification when `lark-cli` is missing or the send fails; `AGENT_LORD_RESULT_ALERT_COMMAND` or `result_alert_command` replaces both. This catches a scheduling session that died while its tasks finished; tasks outside every run are not watched.

`checkpoint` wakes the caller for terminal or model-actionable state and otherwise returns `CHECKPOINT_QUIET` with exit `124` after its quiet window, 600 seconds by default. Quiet is neither a provider failure nor evidence of error-free execution; continue with the remaining active selection. An automatic selection with no active task returns quiet immediately; stop that empty loop and reconcile any expected task. [The supervision reference](references/supervision.md) covers multi-task selection, compact output, and recovery supervision.

- Let the host report the checkpoint's completion without extra model calls. Claude Code: run it as a background command, whose completion Claude Code announces. Codex: `exec_command` returns after at most 30 seconds whatever `yield_time_ms` asks, so keep waiting on the returned session with `write_stdin` and empty input, which waits up to `background_terminal_max_timeout` (300 seconds by default). Both are upper bounds that return as soon as the command exits, so a task that finishes early is still reported at once. Keep `--seconds` at the default instead of shortening it to a tool limit: in run-02 a Codex caller chose 50-second checkpoints and spent 816 of its 1,036 tool calls waiting. Use a shorter window only for a user-set interval or a host-required heartbeat.
- Select a registered set with `--run-id`. Without a set, put each id in exactly one selection: `--task-id` for a task whose record is confirmed present, `--starting-task-id` for a just-dispatched task whose record may not exist yet. In `starting[]`, `not_observed` means only that no record appeared in the window; the dispatch command's own exit status decides whether dispatch failed.
- Keep at most one outstanding checkpoint per selected task set; selections that share no task, such as independent runs, may each hold their own. If the host yields a running command handle, resume it until completion before starting that selection's next checkpoint. An unchanged wait does not call for another `check`, log read, or watcher.
- Send a progress message only when `reporting.should_notify` is true or the host requires a heartbeat, and then report only known elapsed time and whether a new result arrived. Keep window numbers internal: they divide supervision waits, not execution stages, retries, or sessions. Report milestones only with concrete artifact or endpoint evidence; `progressing` and `tool_wait` describe activity, not task health. Continue processing `actionable` even when reporting is suppressed.
- At completion, consume the canonical final text once and report the result, artifact location, source SHA when applicable, and the actual model/variant or its verification limit. When assessing delay, separate caller preparation, endpoint execution, and result retrieval using available timestamps and name unmeasured intervals.

## Provider routing and defaults

- Claude Code is an ordinary execution endpoint and may perform any user-assigned implementation, research, review, test, or other node.
- `claude-cli`: default to configured `claude-fable-5` / `xhigh`. A model on the configured 1M list runs as `<model>[1m]` unless its name already sets a window, because Claude Code behind a gateway otherwise assumes 200K; the Fable fallback follows the same rule. Defaults come from the provider configuration, independent of Claude user settings. The default retry plan permits five attempts; a Fable-family primary model adds up to five configured `claude-opus-5` attempts on the same session, and a report names the model that actually ran.
- `codex` or `codex-cli`: use Codex CLI, defaulting to `gpt-6-astra` with `xhigh`. Treat an unqualified user request for “Codex” as this route.
- `mcode` or `mcode-cli`: default to `custom_provider:mafia-claude/claude-opus-5` with `xhigh`. MCode takes the context window from its own model configuration and validates an explicit `--effort` against the model's live options; a `#variant` is part of model identity and never substitutes for `--effort`.
- `codex-app`: use only when the user explicitly requests the App/Desktop endpoint. Existing App task handles remain App tasks.

Explicit user model and effort values override defaults independently, and `--retry-attempts` overrides the primary Claude stage. Every resolved value is frozen at `start`. `config/providers.json` is the executable source of truth for these policies; [the execution contract](references/protocol.md#execution-contract) records how each is enforced and verified.
