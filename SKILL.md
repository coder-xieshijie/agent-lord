# Agent Lord

Manage multiple related or independent tasks from one scheduling session, with one logical task per durable endpoint. Treat `node core/dist/cli.js` as the control plane: the model supplies intent and performs Codex App host-tool actions when requested, while the script owns provider defaults, validation, retries, state, recovery, and artifact extraction.

## Scheduling ownership

The originating user-facing session is the sole scheduling caller. It directly dispatches every execution endpoint and owns task decomposition, provider/model selection, continuation, recovery, supervision, artifact exchange, and pipeline progression. Do not delegate those responsibilities to a coordinator CLI.

Each dispatched CLI receives one concrete execution task, which may include implementation, analysis, review, testing, and authorized delivery. Include the following executor constraint in the hard constraints of every caller-authored CLI prompt, including later turns and handoff packets; the executor need not load this Skill to receive it:

> You are an execution endpoint. Complete only your assigned task. Do not invoke Agent Lord or another agent entry point to delegate work or create, continue, recover, or supervise other agent tasks. If the task needs splitting or help, return that need and relevant context to the scheduling caller. The caller owns scheduling and workflow progression.

### Tasks added during execution

When the user steers the scheduling session, classify the instruction as a change to an existing task, a new related task, or a new independent task. Preserve existing tasks and their supervision unless the user explicitly cancels or replaces them.

- For a new task, use a new `task_id` and dispatch it when its dependencies and workspace contract permit; independent additions can start while earlier CLIs are still running. Keep unrelated goals in separate task sets or runs. For a related addition, update the affected run manifest, dependencies, and artifact exchange before dispatch, preserving existing endpoint contracts and authorization boundaries.
- For an existing task, continue its saved endpoint with `turn` after the current operation is terminal, following the normal continuation/error rules. While it is running, register the instruction in the [request inbox](#deferred-instruction-inbox) so it survives compaction or a restart. Agent Lord still has no in-flight steer: a registered request never reaches the running CLI, and the instruction stays pending until you dispatch it yourself.
- After adding endpoints, include every active task managed by this caller in the next `checkpoint` selection, across runs, and pass each newly starting `task_id` as `--starting-task-id` so the window before its records exist is supervised too. An outstanding checkpoint keeps its original selection; resume its handle until it returns, then refresh the set under the [waiting rules](#waiting-and-reporting). Update the [observer binding](#read-only-live-observer) for the added tasks unless background-only execution was requested.

### Deferred instruction inbox

When the user adds work you cannot dispatch yet, register it instead of holding it only in conversation context. The inbox is passive: it never dispatches, never polls, and never injects anything into a running operation.

```bash
node core/dist/cli.js request-add --request-id followup-1 --intent turn \
  --task-id refactor-auth --message-file /private/tmp/followup.txt \
  --user-request-file /private/tmp/user-said.txt --source-kind codex
node core/dist/cli.js request-list --status pending
node core/dist/cli.js request-dispatch --request-id followup-1 --include-response
```

- Use `--intent start` with the same `--provider`, `--target`/`--repo`, model, workspace, and delivery flags `start` accepts for a task that does not exist yet; use `--intent turn` for a later turn on a saved endpoint. Those options are frozen at registration and validated against the live execution contract at dispatch, not before.
- Report a registered request as pending, not as dispatched or delivered. `request-dispatch` returns `REQUEST_PENDING` when the target task is still busy: keep it pending and retry after the current operation is terminal. Cancel with `request-cancel` when the user withdraws it; a request that already produced an operation cannot be cancelled.
- The registered `request_id` is written into the operation record itself, so repeating `request-dispatch` after a crash, a provider failure, or an unknown delivery returns the original operation instead of opening a second turn. Never work around `DELIVERY_UNKNOWN` by registering or dispatching the same instruction again; follow the normal recovery decision.

## Runtime setup

Use Node.js 24 or newer. From this Skill's repository root, run `pnpm install --frozen-lockfile` and `pnpm --filter @agent-lord/core build` after installation or source updates. Invoke the compiled CLI from this root; when calling it elsewhere, use its absolute path. Provider binaries still come from the terminal environment or the configured `AGENT_LORD_*_BIN` variables.

For an existing Python installation, drain its running controllers and provider processes before switching the shared state directory to TypeScript. The JSON formats and endpoint identities stay compatible; process-lock implementations must not be mixed. See the [migration guide](references/python-to-typescript.md) for cutover and rollback steps.

## Invariants

- Use scripts, CLI and authenticated HTTP for dispatch, supervision and observer verification. Agent Lord must not invoke or depend on Computer Use, CUA or browser automation, including as a fallback. A supported host link-opening API is presentation only; visible-page confirmation is not a completion requirement.
- Keep the delegated task's implementation, analysis, review, test execution, and semantic acceptance in the user-authorized external endpoints unless the user explicitly asks the caller to take over in the current session. The scheduling caller handles context transfer, dispatch, supervision, and result convergence, and may directly inspect dispatch contracts, run records, and deliverable completeness or review the orchestration process itself. These control-plane checks do not authorize adding workflow nodes.
- Start only with explicit user authorization. Preserve user choices for target, source revision, model, effort, task scope, and external writes.
- Use `dangerously_bypass` for every new local CLI dispatch, including reviews and handoffs; omit `--read-only`. Express read-only review, no-code-change, and external-write restrictions in the task prompt. These semantic limits remain binding; they do not make the process read-only or expand authority for external writes.
- Treat the user-specified endpoint set as part of the execution contract. Dispatch every requested Codex CLI, Claude Code CLI, or MCode CLI endpoint exactly; never drop or substitute a named provider.
- Keep one endpoint per `task_id` and one in-flight operation per task. Continue the saved endpoint; replacement requires an explicit decision.
- Let the dispatch lock and operation journal enforce that invariant across concurrent controller processes; do not implement a second caller-side lock.
- Let operation-scoped workspace and branch write leases serialize local CLI tasks. Bypass processes, including reviews, are writable to the runtime and hold exclusive leases; concurrent tasks need separate worktrees and checkout branches. An unfenced writable operation keeps blocking new writers until `checkpoint` fences it.
- Store task, operation, action, event, log, and artifact state under `${AGENT_LORD_STATE_DIR:-$HOME/.codex/state/agent-lord}`, never in the target repository.
- Freeze the resolved model, effort, retry plan, permission posture, and source contract when the task starts; every later turn reapplies them.
- Use fixed full SHAs for revision-sensitive work. Review prompts require an unchanged checkout at the frozen head; verify that scope before accepting review artifacts. The runtime permits a writable repo-managed task to advance only on its contract checkout branch as a descendant of the last verified head, which becomes the new verification baseline. That capability does not authorize a review task to change its source.
- Exchange sanitized artifacts, not raw provider logs or reasoning traces.
- Treat the caller's task set, dependencies, disjoint output boundaries, next-step policy, or explicitly named built-in pipeline as inputs. Agent Lord supervises endpoint operations; it does not invent an unnamed workflow.
- The workflow is user input unless the user invokes a documented named pipeline. Preserve every explicit dependency, sequence, node, role, and completion condition. Multiple named actions that the caller identifies as independent, or whose dependency relationship is genuinely unclear, create a dispatch decision before execution: run confirmed-independent actions concurrently under a valid workspace contract; ask the caller when independence is unclear. Absence of an explicit parallel keyword is not a reason to silently serialize confirmed-independent actions.
- Resolve that dispatch decision before starting the first execution endpoint. Create required isolation under the workspace policy below. When concurrency requires an integrator, merge order, or another workflow expansion that the caller did not authorize, report that expansion and obtain the caller's decision. Do not choose serial execution merely to avoid that decision.
- Add no planner, reviewer, tester, audit, acceptance, or other “best practice” node on your own. Ordinary risk judgement is grounds for reporting a concern to the user, never for extending the workflow.
- Internal `task_id` and endpoint operations are execution-control handles only. Creating, retrying, or recovering one grants no authority to add a user-visible workflow node; a new node requires an explicit user flow or a later explicit instruction.

## Pipeline routing

- For every multi-endpoint or named pipeline, read [references/pipelines/common.md](references/pipelines/common.md) and freeze its run manifest, barriers, role checks, convergence bound, and final deliverable before dispatch.
- When the request says “交叉 Review”, “交叉审查”, or `cross-review`, also read [references/pipelines/cross-review.md](references/pipelines/cross-review.md) and execute its MCode Fable 5 `xhigh` + Codex `gpt-6-astra` / `max` mutual-review → independent new-session MCode Fable 5 `xhigh` check policy. The phrase authorizes only the nodes documented there; explicit user overrides still win.
- When the request says “handoff” or “交接”, or asks to hand the current session's work to a new local CLI that continues a user-named task, read [references/pipelines/handoff.md](references/pipelines/handoff.md) as the complete handoff authoring and execution contract, then use the `handoff` command with a sanitized `handoff-v1` packet. The phrase authorizes exactly one new local CLI continuation endpoint — a sanitized context transfer with new-endpoint lineage, never a session migration; explicit user overrides still win.

## Deterministic loop

1. Resolve the exact repository, source branch, and fixed head/base. Batch independent repository and provider-discovery reads; keep source resolution and dispatch in dependency order. Reuse skill instructions and command help already verified in this session while their source/version is unchanged; refresh mutable repository and provider facts needed for this dispatch. For an unknown MCode model identifier, query `mcode provider list --json` directly and retain only the relevant provider/model/variant fields. Leave delegated code investigation to the endpoint.
2. Write a compact task prompt with five parts: goal, source revision, scope, hard constraints, and deliverables. State this endpoint's assignment, required dependency artifacts, and output boundaries; pass only the context needed for that assignment. Include the [executor constraint](#scheduling-ownership) in the hard constraints. Preserve all user requirements and necessary evidence or artifact pointers once; omit repeated conversation history and duplicate instructions. Record the user's exact request in a private `--invocation-file` JSON with `user_request` and `trigger: "user_request"`; for caller-authored follow-ups use `trigger: "caller_followup"` and a short `reason`. Caller identity is captured from the host environment unless explicitly supplied; do not invent missing ids. Keep input files outside the repository and remove caller-owned files in the result-retrieval batch. See [invocation metadata](references/protocol.md#invocation-metadata) for the schema and identity limits.
3. Inspect `node core/dist/cli.js start --help` on first use or when the command surface is uncertain or has changed, then run `start` with every explicit user choice. For revision-sensitive local CLI work, use `--repo`, `--source-branch`, one explicit workspace policy, and `--head-sha`; the control plane freezes the resolved checkout as the target. Use `--target` when the exact working directory already is the contract. Do not recreate these preflight checks manually.
4. In Codex Desktop, attach this task or the explicitly requested pipeline task set with [the observer CLI](observer/README.md#派发后的任务绑定) before the first supervision wait. Open its focused link once through the host API; `queued` means only an opening request. Reattach only when the task set changes or the observer needs recovery. The same task's later turns and terminal state use the existing page. Skip automatic setup when the user requests background execution without a page. Retain any running controller handle for later resumption.
5. Pass `--include-response` to `start`, `turn`, `recover`, `handoff` and `accept` as well as `checkpoint`, so a successful return includes the final text. Process the returned envelope until terminal:
   - `ACTION_REQUIRED`: invoke the exact model-side tool and arguments in `action`; save the raw return value outside the repository, then pass it to `accept`. Add `--auto-read` to `accept` when the next step would only be another polling read; the envelope then carries that read action directly instead of requiring a separate `check`.
   - `RUNNING`: supervise local CLI work with one bounded `checkpoint --include-response`, selecting every active `task_id` managed by this caller with `--task-id`, including independent runs, and every just-dispatched `task_id` with `--starting-task-id` for the window before its operation and task records exist. Use `check` for a needed full-state diagnosis of one established task, or to request the next Codex App read when `accept --auto-read` was not used. Only `checkpoint` supervises dead controllers; `check` reports state and, when the recorded controller process is gone, an `observed.supervision.recovery_command` hint.
   - `CHECKPOINT_ACTIONABLE`: process every ordinary envelope in `actionable`.
   - `SUCCEEDED`: consume the canonical `response.text`, artifact and execution evidence from the terminal envelope once. If the command returned no inline text, retrieve it with `check --task-id <id> --include-response`; do not repeat artifact or metadata reads. Inspect `delivery` separately before claiming the requested files or commit are complete. Retrieve any retained controller handle and clean up caller-owned inputs in that same batch; no terminal browser check or duplicate completion ledger is required.
   - `ERROR`: follow `safe_recovery` only when present; otherwise report the structured error. `CONTINUE_SAME_SESSION` means run `recover --task-id <id> --operation-id <failed-id>` under the existing task authorization, then supervise the returned operation. An absent recovery action is not itself a permission request; ask only when new authority is actually needed. The Claude `RESULT_INVALID` retry below is the single documented exception.
   - `NEEDS_DECISION`: stop for the authority named by the error. Never convert it into an implicit replacement, model change, source change, or permission expansion.
6. Start a later round with `turn` only after the previous operation is terminal. Record its request source/reason with `--invocation-file`, then supervise using the existing observer binding. The script reapplies the saved execution contract and deduplicates an identical in-flight message. For concrete local CLI deliverables, declare each non-empty workspace-relative file with `--require-file` and a new clean commit with `--require-commit` on `start` or `turn`. These structural checks do not establish test results, UI quality, or semantic acceptance.

## Claude `RESULT_INVALID` retry

The user authorizes one bounded exception to the `ERROR` rule above: any `claude-cli` operation whose terminal error code is `RESULT_INVALID`, whatever its message, may be retried. It covers every Claude Code role. The control plane still terminalizes that operation and still emits no `safe_recovery`; the retry is consumed with the dedicated command `retry-invalid --task-id <id> --operation-id <failed-id>`, which owns the persistent budget, the fingerprint comparison, and the lineage record — do not keep a second manual ledger for them. See [the retry-invalid contract](references/protocol.md#scripted-claude-result_invalid-retry) for the exact persisted semantics.

- **Budget.** Three retry attempts after the original failure, counted across every session for that one logical operation and persisted on the lineage-root operation record. The command stops immediately on success and refuses with `RETRY_BUDGET_EXHAUSTED` after the third retry fails; then report the structured error and preserve unresolved pipeline state.
- **Same endpoint first.** The command retries with `turn` on the same saved `task_id` and provider session, and stays there until the replacement trigger fires. When the failed start never established a durable task record, the same-session path is unavailable and the command refuses with a structured `requires_authorization` decision; passing `--replacement-task-id` explicitly authorizes the replacement session, recorded as `forced_new_session`. This applies to every Claude Code role, including declared parallel-group members.
- **Fingerprint.** Consecutive failed results are compared by the error's `code` plus its `message` and nothing else; per-attempt values are excluded. A different fingerprint resets the consecutive-identical streak.
- **Replacement trigger.** When two consecutive failed results share one fingerprint, the next retry runs in a new Claude session. A `task_id` is never rebound, so the command starts a new `task_id` (derived, or explicit via `--replacement-task-id`), persists its `replacement_for` lineage in the ledger and on the retry operation, and replays only the same authorized logical operation inputs. This policy is the explicit decision that the endpoint-replacement invariant requires. The new session resets the identical-result streak and keeps spending the same three-retry total.
- **Contract.** Same-task and replacement retries alike reapply provider, model, effort, permission posture, target/workspace, fixed source contract, role, semantic scope, and the sanitized inputs the endpoint already had; the command reports any observed `contract_mismatch` in its `invalid_retry` block. They may not add a workflow node, change model, source, or permissions, expose a new peer artifact, or substitute the configured fallback stage for the missing result. A declared parallel-group member retries and replaces like any other role; its `parallel_role` is carried in the ledger, dispatch event, and `invalid_retry` block so the pipeline's identity-continuity checks can re-evaluate the replacement, and any workspace write-lease conflict surfaces as the usual structured lease error.
- **Pipelines.** This budget is separate from any semantic round or convergence bound and never extends one. A replacement session changes endpoint identity: disclose it in `Pipeline Check` and re-evaluate every identity-continuity and role-independence check against the new endpoint, which may no longer satisfy them.

## Workspace and parallel-write policy

- Create task-required worktrees and their isolated local branches for any authorized task without additional user confirmation. Choose distinct temporary branch names when needed. This authorization covers isolation only; it adds no workflow nodes, endpoint replacements, external writes, or exceptions to source checks.
- `reuse-or-create`: reuse the one clean source-branch worktree or create it; writable operations hold exclusive workspace and branch leases until the provider operation ends.
- `isolated`: use a distinct explicit `--workspace-branch` for each concurrent CLI task, including bypass reviews; create or reuse its worktree from the fixed source head. Continue later rounds in that same task's workspace.
- `shared-readonly` and `--read-only` remain low-level compatibility capabilities; do not select them for new Skill dispatches. A strict review prompt cannot satisfy the runtime's read-only requirement for a shared lease.
- Same-MR parallel editing with integrated commits requires caller-declared `--parallel-group`, worker order, one integrator task id, and the original MR source branch as `--integration-target-branch`. Workers use `isolated`; the integrator uses `reuse-or-create` and lists successful worker task ids in order. Concurrent reviews use isolated worktrees without integration metadata or an integrator.
- The caller starts the named integrator only after the workers are terminal. Agent Lord validates the declared barrier and isolation contract; it does not invent workers, an integrator, merge order, or another MR.
- For declared parallel editing, a missing or inconsistent integration plan returns `NEEDS_DECISION`. Read [references/protocol.md](references/protocol.md) before dispatching concurrent writable tasks.

## Waiting and reporting

`checkpoint` wakes the caller for terminal or model-actionable state before its default 120-second quiet deadline. `CHECKPOINT_QUIET` with exit `124` is healthy: continue with the remaining active task selection. An automatic selection with no active task returns quiet immediately; stop that empty loop and reconcile any expected task. Read the protocol reference for multi-task selection, compact output, and recovery supervision semantics.

- Codex callers use `checkpoint --seconds 120 --include-response` for the first supervision wait and every later wait, including after continuation or recovery. Change the duration only when the user explicitly requests another interval. Select established tasks with `--task-id`, which still fails on an unknown id, and each task you just dispatched with `--starting-task-id`, which tolerates a record that has not appeared yet. Read `starting[]` on return: `not_observed` means only that no record was seen in the window, so use the dispatch command's own exit status and error envelope to decide whether the dispatch actually failed.
- Keep one outstanding checkpoint for the selected task set. If the host tool yields a running command handle, resume that handle until completion; start the next checkpoint only after it returns. Preserve the checkpoint's quiet deadline when adapting host-tool wait/yield windows to responsiveness or heartbeat requirements. An unchanged wait does not call for another `check`, log read, or watcher.
- Report dispatch and meaningful changes such as a new deliverable, recovery, a required decision, or completion. When host instructions require a heartbeat, use elapsed time and the latest content-free activity summary (`last_tool`, `active_tool_count`, `last_event_type`, `progress_age_seconds`) when available; label stale observations and do not infer current tool activity from silence. An event count alone does not describe progress. Use available metadata instead of extra queries solely to fill a progress message.
- At completion, consume the canonical final text once (prefer the inline response) and report the result, artifact location, source SHA when applicable, and actual model/variant or its verification limit. When assessing delay, separate caller preparation, endpoint execution, and result retrieval using available timestamps; identify unmeasured intervals. Shorter polling does not make the endpoint execute faster, and any speedup target remains unverified until measured.

## Provider routing and defaults

- Claude Code is an ordinary execution endpoint and may perform any user-assigned implementation, research, review, test, or other node. This execution role is independent of Fable decision routing.
- `claude-cli`: default to configured `claude-fable-5` / `xhigh`. The active `provider-config` resolution policy keeps Agent Lord defaults independent of Claude user settings; `claude-user-settings` remains available for installations that opt into per-field settings resolution. Freeze both resolved values at `start`.
- Explicit Claude model and effort arguments override independently; unspecified fields follow the configured resolution policy. When both are explicit, both win. The default retry plan permits five attempts. When the explicit or resolved primary model belongs to the Fable family, five failed attempts are followed by up to five configured `claude-opus-5` attempts on the same session; report that fallback as the model that actually ran.
- `codex` or `codex-cli`: use Codex CLI, defaulting to `gpt-6-astra` with `xhigh`. Treat an unqualified user request for “Codex” as this route.
- `mcode` or `mcode-cli`: default to `custom_provider:mafia-claude/claude-fable-5#xhigh`. An explicit `provider/model` or `provider/model#variant` replaces that entire default, including its variant. MCode exposes no independent effort control, so omit `--effort`. A specified variant is frozen and verified from the terminal result; an omitted variant remains explicitly unverified.
- `codex-app`: use only when the user explicitly requests the App/Desktop endpoint. Existing App task handles remain App tasks.

Explicit user values override defaults. `--retry-attempts` overrides the primary Claude stage; the configured Fable fallback budget remains independent. `config/providers.json` is the executable source of truth for these policies.

## Local CLI adapters

The mappings below describe runtime capabilities, including retained read-only compatibility; new Skill dispatches follow the bypass invariant above. Existing tasks continue under their frozen contracts.

Claude maps `dangerously_bypass` to `--dangerously-skip-permissions`; `--read-only` maps to `--permission-mode plan`. Every initial, resumed, retried, or recovered Claude process receives the frozen model/effort arguments and a child-only environment that defers settings-owned model/route values to Claude's user configuration while preserving credentials, custom headers/base URL, helpers, and config location. It verifies the main model from same-session `system` / `assistant` / `result` metadata; a requested context modifier such as `[1m]` additionally requires matching context-capability evidence. A failed auxiliary `auto_mode` model is published as a sanitized warning when the matching main result succeeded; it does not consume retry budget or trigger fallback. Claude journals streaming progress and retries or recovers only on the saved session under the frozen contract. Read the protocol reference when diagnosing stalls, controller takeover, or retry exhaustion.

Codex CLI maps `dangerously_bypass` to `--dangerously-bypass-approvals-and-sandbox`; `--read-only` applies explicit sandbox and approval config arguments. It runs `codex exec --json`, stores `thread.started.thread_id` as endpoint identity, publishes only `--output-last-message`, and continues through `codex exec resume <session-id>` while reapplying model, effort, and permissions. A `preparing` operation whose controller died is supervised by `checkpoint`: never-launched work is retryable, and a possibly-launched one becomes `DELIVERY_UNKNOWN`.

MCode maps `dangerously_bypass` to `--permission full`; this records MCode permission-policy enforcement and does not claim that every sandbox is disabled. MCode read-only is unsupported because `smart`, `full`, and `off` do not enforce read-only, so `--read-only` fails before dispatch. The adapter uses `mcode exec --input - --cwd ... --model ... --output-format stream-json --output-last-message ...`, resumes only through the saved `--session`, and strictly binds schema-version-1 Session/Turn/Run identities, terminal status, actual model/variant, exit code, and final file. Read the protocol reference for recovery boundaries.

## Codex App action handshake

Codex App host tools are model-side tools, so the script emits an action instead of guessing a shell bridge. The model is a transport carrier:

1. Call exactly `action.tool` with `action.arguments`.
2. Preserve the complete raw tool result in a temporary file outside the repository.
3. Run `node core/dist/cli.js accept --action-id <id> --result-file <file>`; add `--auto-read` when you only intend to keep polling the same thread.
4. Continue from the new envelope.

The App adapter uses only the supported minimal `list_threads` arguments, treats `threadId` as endpoint identity and `hostId` as mutable routing, and rebinds the same thread before retrying a route-stale send. A transiently failed listing is re-issued within a small bounded budget instead of terminalizing the operation. Its action schema has no sandbox or approval field, so bypass is recorded as `host-inherited-unverified` and read-only remains instruction-only.

## Artifacts and compatibility

Successful local CLI turns automatically publish a final-response-only artifact. Codex App reads do the same; `export-artifact` can extract the final assistant message and model/effort metadata from an existing Claude or Codex JSONL without copying reasoning. A Codex export must contain the exact operation marker, and a Claude export must be a `claude-jsonl` log whose assistant records carry this operation's own session id, so an unrelated turn cannot be mistaken for this result. MCode stream JSON has no independently verifiable Agent Lord operation marker, so `mcode-stream-json` auxiliary import is explicitly refused; the direct adapter remains the canonical artifact path. `export-artifact` is auxiliary: a rejected export never invalidates an already-succeeded operation or its artifact. A Claude session log cannot prove effort, so the export publishes an explicit `EFFORT_UNVERIFIABLE_FORMAT` warning instead of inventing one; the contract itself is still argument-enforced at dispatch.


Version 1 task handles remain readable, but `turn` fails closed because those records did not preserve model, effort, permission, or source. Use `node core/dist/task-store.js upgrade` with explicit values before continuing one; it never infers the missing contract. The compatibility interface also supports explicit registration and cleanup; new work uses `node core/dist/cli.js`.

## Read-only live observer

The observer is a TypeScript/Node service with React and vendored Vercel AI Elements components. Build with `cd observer && pnpm install --frozen-lockfile && pnpm build` when its dependencies or compiled assets are missing or stale. Use `preview:attach` for HTTP-verified task binding and a focused URL; the host link API only requests display. [Observer instructions](observer/README.md#派发后的任务绑定) define reuse and failure handling. The launcher checks authenticated instance identity and PID before stopping a service.

The loopback view combines an explicit task allowlist, journal/native exec projections, snapshot, cursor and SSE. It observes Codex CLI, Claude Code and MCode output; Codex App has state only. The view remains read-only: it never runs checks, checkpoints, recovery, or prompts. It separates execution status from declared delivery evidence and provides native terminal resume commands when Session identity is available. Private runtime files live under `<state>/observer/`; stopping the observer leaves the tasks running. Read [observer/README.md](observer/README.md) for setup, privacy boundaries, lifecycle commands, and the component provenance/license.

Read [references/protocol.md](references/protocol.md) when supervising multiple tasks, diagnosing stalls, errors, or recovery, or changing an adapter or state record. Ordinary single-task `RUNNING` supervision follows the loop above. The reference is the source of truth for actionability, recovery, schemas, and error semantics.
