# Agent Lord

Manage multiple related or independent tasks from one scheduling session, with one logical task per durable endpoint. Treat `node core/dist/cli.js` as the control plane: the model supplies intent and performs Codex App host-tool actions when requested, while the script owns provider defaults, validation, retries, state, recovery, and artifact extraction.

For explanations and reports addressed to the user, read and apply the installed `explain-as-fool` Skill under the [dependency contract](#skill-dependencies). Include its resolved readable path in the prompt of any endpoint writing that material, including later turns. Pipeline-specific review and plan standards are named at their point of use.

## Skill dependencies

Agent Lord depends on three Skills maintained in [dev-skills](https://github.com/coder-xieshijie/dev-skills). Install them before use following the [quick start](README.md#2-install-the-required-skills). Agent Lord owns scheduling and pipeline stages; dev-skills owns the shared content standards. This repository does not maintain copies of those standards.

| Skill             | Apply when                                                           | Default installed entry                     |
| ----------------- | -------------------------------------------------------------------- | ------------------------------------------- |
| `review-rules`    | Reviewing findings, proposed fixes, cross-exams, and checker results | `~/.agents/skills/review-rules/SKILL.md`    |
| `plan-for-agents` | Writing or checking a plan's content and completeness                | `~/.agents/skills/plan-for-agents/SKILL.md` |
| `explain-as-fool` | Writing explanations and reports for the user                        | `~/.agents/skills/explain-as-fool/SKILL.md` |

Before the affected assignment, the scheduling caller resolves each required Skill from an explicit user-provided location or the host's registered Skill path, otherwise from the default entry above. Resolve symlinks to actual absolute paths and verify that the execution endpoint can read the Skill and any required relative references. A path readable by the caller alone is insufficient; another machine or sandbox needs its own accessible installation or a run-local snapshot retaining the Skill's relative layout.

Read and apply these files as the assignment's content standards. Pass their absolute paths, required reading, and scope in the prompt; naming a Skill alone does not load it. This does not automatically invoke a separate workflow, add roles, or change a Skill's explicit-invocation setting. The runtime delivers the caller-authored prompt; it does not discover or install these dependencies.

Record resolved paths and content hashes in the run's input versions, with the dev-skills commit when available. Keep the same content for later turns and replacement endpoints. If an installed source changes during a run, use the recorded revision or a retained run-local snapshot, including required supporting files; do not silently continue with new rules. Run snapshots are execution inputs, not maintained rule copies in this repository.

If a required Skill or reference is missing or unreadable, name it and the affected assignment and stop that assignment until resolved. Do not substitute a repository copy or automatically install/update Skills during a task. Unaffected work may continue within the existing workflow.

## Scheduling ownership

The user-facing Codex Desktop, Codex CLI, Claude Code, or MCode session explicitly assigned scheduling by the user is the sole Agent Lord scheduling caller. A user may give this role to a previously resumed execution session; that explicit assignment supersedes its earlier execution-only role for the new workflow. It directly dispatches every Agent Lord execution endpoint and owns user-level assignments, provider/model selection, continuation, recovery, supervision, artifact exchange, and pipeline progression. Do not delegate those Agent Lord responsibilities to a coordinator CLI.

Give each CLI the goal, necessary context, expected outcome, and boundaries required by the user, authorization, or shared-workspace coordination. The CLI owns its internal decomposition, implementation, tool choices, native subagents, and validation approach. Leave healthy execution alone; intervene when the user changes direction or verified failure calls for recovery. Caller preferences for algorithms, libraries, command sequences, output chunk sizes, or test counts are not task constraints unless the user requires them.

Explicitly carry the user's subagent instructions into every applicable task prompt, including later turns and handoffs; never omit or weaken them. Permission leaves the choice to the CLI. A preference prioritizes suitable delegation; include the requirement to briefly explain non-use. An explicit assignment requires the specified subagent work and must not become optional. Include the concrete assignment and any user-specified subagent model or effort. Leave unspecified execution details to the CLI. These instructions govern native subagents within the assignment; they do not authorize additional Agent Lord endpoints.

Each dispatched CLI receives one concrete execution task, which may include implementation, analysis, review, testing, and authorized delivery. Include the following executor constraint in the hard constraints of every caller-authored CLI prompt, including later turns and handoff packets; the executor need not load this Skill to receive it:

> Do not invoke Agent Lord, directly or through a subagent. Return requests for additional execution endpoints or scheduling workflow changes to the scheduling caller.

Native subagents are internal execution of the assigned task, not additional Agent Lord endpoints or caller-level workflow nodes. The assigned scope, source, and write constraints still apply. During supervision, native `task` / `Task` / `Agent` use alone is not a delegation violation and does not require the execution endpoint to repeat the work.

### Task context preparation

The scheduling caller authors the task prompt; the runtime delivers it without selecting or summarizing documents. Cover the following content as applicable, combining it for simple tasks rather than imposing five headings or empty sections:

- **Goal and continuation state:** what this endpoint takes over, verified completed work, remaining work, and where its assignment ends. Include history only when it affects this execution.
- **Current decisions and authorization:** confirmed user choices, scope, write/publication authority, and the concrete [subagent instructions](#scheduling-ownership). Distinguish user decisions from assistant proposals and unresolved questions.
- **Versions and input index:** relevant source/document versions and accessible paths, each material's purpose and authority, and required reading or the condition that triggers it. Distinguish the checkout to modify from any reference source revision; check source claims against the assigned revision.
- **Deliverables and completion criteria:** required outputs, checks, publication steps, and evidence of completion. Distinguish delivered artifacts from working records.
- **Executor constraint:** include the [fixed constraint](#scheduling-ownership) without expanding it into general execution advice.

Prepare that content with these rules:

- Resolve superseded instructions using existing user decisions and identify the currently effective requirements. Label obsolete instructions in referenced history; preserve original evidence. Keep genuine unresolved conflicts explicit rather than inventing a decision or handing down contradictory commands as equally current.
- Reference applicable Skills and repository rules by accessible path and scope. Inline concrete task requirements, explicit overrides, and necessary content the endpoint cannot access; avoid copying general procedures already supplied by those references. Binding decisions must not be hidden behind optional reading.
- Preserve complete source documents; a caller summary never replaces a document the user or a named pipeline requires in full. Require complete reading only then; otherwise state each document's purpose and let the endpoint read what the task needs. Keep detailed evidence in referenced materials rather than duplicating it in the prompt.
- Deliver audit records when required by the user, a named pipeline, or an actual review/handoff need. Otherwise keep process notes in existing working records; a self-check alone does not require a new repository artifact or an additional reviewer or workflow stage.

Before dispatch, verify indexed files are readable from the endpoint's environment. Use [declared inputs](#declared-task-inputs) for required files inside its workspace; check external files separately. When paths are inaccessible or a frozen input snapshot is required, provide an accessible copy or the necessary inline content. Keep referenced inputs available for the duration of execution.

Later turns on the same endpoint may provide an explicit delta identifying what it changes in the existing task contract. Fresh endpoints and handoffs need enough current context to execute independently. In both cases preserve every still-applicable user requirement and include the executor constraint and applicable subagent instructions.

### Tasks added during execution

When the user steers the scheduling session, classify the instruction as a change to an existing task, a new related task, or a new independent task. Preserve existing tasks and their supervision unless the user explicitly cancels or replaces them.

- For a new task, use a new `task_id` and dispatch it when its dependencies and workspace contract permit; independent additions can start while earlier CLIs are still running. Keep unrelated goals in separate task sets or runs. For a related addition, update the affected run manifest, dependencies, and artifact exchange before dispatch, preserving existing endpoint contracts and authorization boundaries.
- For an existing task, continue its saved endpoint with `turn` after the current operation is terminal, following the normal continuation/error rules. While it is running, register the instruction in the [request inbox](#deferred-instruction-inbox) so it survives compaction or a restart. Agent Lord still has no in-flight steer: a registered request never reaches the running CLI, and the instruction stays pending until you dispatch it yourself.
- After adding endpoints, include every active task managed by this caller in the next `checkpoint` selection, across runs, selecting each task exactly once under the [waiting rules](#waiting-and-reporting). An outstanding checkpoint keeps its original selection; resume its handle until it returns, then refresh the selection. For a run-bound observer, `run-add` synchronizes visibility automatically and returns binding verification; recover an unverified binding separately from execution. For a task-only observer, update its explicit binding. Honor background-only execution.

### Deferred instruction inbox

When the user adds work you cannot dispatch yet, register it instead of holding it only in conversation context. The inbox is passive: it never dispatches, never polls, and never injects anything into a running operation.

```bash
node core/dist/cli.js request-add --request-id followup-1 --intent turn \
  --task-id refactor-auth --message-file /private/tmp/followup.txt \
  --user-request-file /private/tmp/user-said.txt --source-kind codex
node core/dist/cli.js request-list --status pending
node core/dist/cli.js request-dispatch --request-id followup-1 --include-response
```

- Use `--intent start` with the same `--provider`, `--target`/`--repo`, model, workspace, and delivery flags `start` accepts for a task that does not exist yet; use `--intent turn` for a later turn on a saved endpoint. Those options are frozen at registration and validated against the live execution contract at dispatch, not before.
- Report a registered request as pending, not as dispatched or delivered. `request-dispatch` returns `REQUEST_PENDING` when the target task is still busy: keep it pending and retry after the current operation is terminal. Cancel with `request-cancel` when the user withdraws it; a request that already produced an operation cannot be cancelled.
- The registered `request_id` is written into the operation record itself, so repeating `request-dispatch` after a crash, a provider failure, or an unknown delivery returns the original operation instead of opening a second turn. Never work around `DELIVERY_UNKNOWN` by registering or dispatching the same instruction again; follow the normal recovery decision.

### Declared task inputs

When a task relies on specific local source files, declare them with repeatable `--require-input` on `start` or `turn` (also supported by `request-add`). Paths are relative to the execution workspace. The runtime checks readability and nonzero size before launching and records path, bytes, and SHA-256. This verifies that the caller supplied the declared material, not its semantic completeness; it does not restrict the CLI's implementation or later edits. See [input preflight](references/protocol.md#declared-input-preflight).

## Runtime setup

Use Node.js 24 or newer. From this Skill's repository root, run `pnpm install --frozen-lockfile` and `pnpm --filter @agent-lord/core build` after installation or source updates. Invoke the compiled CLI from this root; when calling it elsewhere, use its absolute path. Provider binaries still come from the terminal environment or the configured `AGENT_LORD_*_BIN` variables.

For an existing Python installation, drain its running controllers and provider processes before switching the shared state directory to TypeScript. The JSON formats and endpoint identities stay compatible; process-lock implementations must not be mixed. See the [migration guide](references/python-to-typescript.md) for cutover and rollback steps.

## Invariants

- Use scripts, CLI and authenticated HTTP for dispatch, supervision and observer verification. Agent Lord must not invoke or depend on Computer Use, CUA or browser automation, including as a fallback. A supported host link-opening API is presentation only; visible-page confirmation is not a completion requirement.
- Keep the delegated task's implementation, analysis, review, test execution, and semantic acceptance in the user-authorized external endpoints unless the user explicitly asks the caller to take over in the current session. The scheduling caller handles context transfer, dispatch, supervision, and result convergence, and may directly inspect dispatch contracts, run records, and deliverable completeness or review the orchestration process itself. These control-plane checks do not authorize adding workflow nodes.
- Start only with explicit user authorization. Preserve user choices for target, source revision, model, effort, task scope, and external writes.
- Use `dangerously_bypass` for every new local CLI dispatch, including reviews and handoffs; omit `--read-only`. Express read-only review, no-code-change, and external-write restrictions in the task prompt. These semantic limits remain binding; they do not make the process read-only or expand authority for external writes.
- Treat the user-specified endpoint set as part of the execution contract. Dispatch every requested Codex CLI, Claude Code CLI, or MCode CLI endpoint exactly; never drop or substitute a named provider.
- Keep one endpoint per `task_id` and one in-flight operation per task. Prefer continuing the saved endpoint; when necessary, replace it under [endpoint replacement](#endpoint-replacement) without additional user confirmation.
- Let the dispatch lock and operation journal enforce that invariant across concurrent controller processes; do not implement a second caller-side lock.
- Let operation-scoped workspace and branch write leases serialize local CLI tasks. Bypass processes, including reviews, are writable to the runtime and hold exclusive leases; concurrent tasks need separate worktrees and checkout branches. An unfenced writable operation keeps blocking new writers until `checkpoint` fences it.
- Store task, operation, action, event, log, and artifact state under `${AGENT_LORD_STATE_DIR:-$HOME/.codex/state/agent-lord}`, never in the target repository.
- Freeze the resolved model, effort, retry plan, permission posture, and source contract when the task starts; every later turn reapplies them.
- Use fixed full SHAs for revision-sensitive work. Review prompts require an unchanged checkout at the frozen head; verify that scope before accepting review artifacts. The runtime permits a writable repo-managed task to advance only on its contract checkout branch as a descendant of the last verified head, which becomes the new verification baseline. That capability does not authorize a review task to change its source.
- Exchange sanitized artifacts, not raw provider logs or reasoning traces.
- Treat the caller's task set, dependencies, disjoint output boundaries, next-step policy, or explicitly named built-in pipeline as inputs. Agent Lord supervises endpoint operations; it does not invent an unnamed workflow.
- The workflow is user input unless the user invokes a documented named pipeline. Preserve every explicit dependency, sequence, node, role, and completion condition. Multiple named actions that the caller identifies as independent, or whose dependency relationship is genuinely unclear, create a dispatch decision before execution: run confirmed-independent actions concurrently under a valid workspace contract; ask the caller when independence is unclear. Absence of an explicit parallel keyword is not a reason to silently serialize confirmed-independent actions.
- Resolve that dispatch decision before starting the first execution endpoint. Create required isolation under the workspace policy below. When concurrency requires an integrator, merge order, or another workflow expansion that the caller did not authorize, report that expansion and obtain the caller's decision. Do not choose serial execution merely to avoid that decision.
- Add no planner, reviewer, tester, audit, acceptance, or other “best practice” node on your own. Ordinary risk judgement is grounds for reporting a concern to the user, never for extending the workflow.
- Internal `task_id` and endpoint operations are execution-control handles only. Creating, retrying, or recovering one grants no authority to add a user-visible workflow node; a new node requires an explicit user flow or a later explicit instruction.

## Deterministic loop

Execution is decoupled from waiting: a new CLI dispatch returns a `RUNNING` receipt while a detached controller keeps executing; collect terminal state with `checkpoint`. A host wait timeout ends only the wait, never the execution. The retained controller handle mentioned below applies only to pre-upgrade dispatches still running and to checkpoints that have not yet returned. Plan-integration recovery uses [plan-integration-resume](references/pipelines/plan-to-implement.md#final-integration), which preserves established delivery facts instead of clearing progress with a reset.

1. Resolve the exact repository, source branch, and fixed head/base. Batch independent repository and provider-discovery reads; keep source resolution and dispatch in dependency order. Reuse skill instructions and command help already verified in this session while their source/version is unchanged; refresh mutable repository and provider facts needed for this dispatch. For an unknown MCode model identifier, query `mcode provider list --json` directly and retain only the relevant provider/model/variant fields. Leave delegated code investigation to the endpoint.
2. Author the task prompt using [task context preparation](#task-context-preparation). Record the user's exact request in a private `--invocation-file` JSON with `user_request` and `trigger: "user_request"`; for caller-authored follow-ups use `trigger: "caller_followup"` and a short `reason`. Record the scheduling client and its own Session identity using the [caller binding contract](references/protocol.md#invocation-metadata). Codex auto-detection is retained; Claude Code and MCode supply an explicit `caller` or the documented `AGENT_LORD_CALLER_*` environment binding. Verify the returned `invocation.caller` matches the current scheduler; unavailable identity must be reported, never guessed from the latest session. Keep input files outside the repository and remove caller-owned files in the result-retrieval batch. See [invocation metadata](references/protocol.md#invocation-metadata) for the schema and identity limits.
3. Inspect `node core/dist/cli.js start --help` on first use or when the command surface is uncertain or has changed, then run `start` with every explicit user choice. For revision-sensitive local CLI work, use `--repo`, `--source-branch`, one explicit workspace policy, and `--head-sha`; the control plane freezes the resolved checkout as the target. Use `--target` when the exact working directory already is the contract. Do not recreate these preflight checks manually.
4. From every scheduling client, bind a task set once with `pnpm --dir <agent-lord-root>/observer preview:attach --run-id <run>` using [the observer CLI](observer/README.md#task-binding-after-dispatch) before the first supervision wait; replace `<agent-lord-root>` with the absolute repository path and use `--tasks` for an individual task. Verify `binding_verified` and every requested task in the returned list. Open its focused link once through the host API when available; otherwise return the local link to the user. `queued` means only an opening request. A run subscription follows later registered members automatically; reattach when adding another run, changing task-only selection, or recovering the observer. The same task's later turns and terminal state use the existing page. Skip automatic setup when the user requests background execution without a page. Retain any running controller handle for later resumption.
5. Pass `--include-response` to `start`, `turn`, `recover`, `handoff` and `accept` as well as `checkpoint`, so a successful return includes the final text. Process the returned envelope until terminal:
   - `ACTION_REQUIRED`: invoke the exact model-side tool and arguments in `action`; save the raw return value outside the repository, then pass it to `accept`. Add `--auto-read` to `accept` when the next step would only be another polling read; the envelope then carries that read action directly instead of requiring a separate `check`.
   - `RUNNING`: supervise local CLI work with bounded `checkpoint --include-response` waits that cover every active task managed by this caller, including independent runs, in exactly one selection each under the [waiting rules](#waiting-and-reporting). Use `check` for a needed full-state diagnosis of one established task, or to request the next Codex App read when `accept --auto-read` was not used. Only `checkpoint` supervises dead controllers; `check` reports state and, when the recorded controller process is gone, an `observed.supervision.recovery_command` hint — see [`check` versus `checkpoint`](references/supervision.md#check-versus-checkpoint).
   - `CHECKPOINT_ACTIONABLE`: process every ordinary envelope in `actionable`.
   - `SUCCEEDED`: consume the canonical `response.text`, artifact and execution evidence from the terminal envelope once. If the command returned no inline text, retrieve it with `check --task-id <id> --include-response`; do not repeat artifact or metadata reads. Inspect `delivery` separately before claiming the requested files or commit are complete. Retrieve any retained controller handle and clean up caller-owned inputs in that same batch; no terminal browser check or duplicate completion ledger is required.
   - `ERROR`: consume an offered `safe_recovery` when appropriate. `CONTINUE_SAME_SESSION` means run `recover --task-id <id> --operation-id <failed-id>`, then supervise the returned operation. Otherwise evaluate [endpoint replacement](#endpoint-replacement) or the Claude `RESULT_INVALID` retry below; report the structured error if neither applies. An absent recovery action is not itself a permission request.
   - `NEEDS_DECISION`: resolve the named decision from existing authorization, including the replacement policy below; ask the user only for authority still missing. Preserve explicit model, source, scope, and permission choices.
6. Start a later round with `turn` only after the previous operation is terminal. Record its request source/reason with `--invocation-file`, then supervise using the existing observer binding. The script reapplies the saved execution contract and deduplicates an identical in-flight message. For concrete local CLI deliverables, declare requested non-empty workspace-relative files with `--require-file` on `start` or `turn`. Add `--require-commit` only when a Git commit is part of the authorized delivery, including named implementation pipelines that require it. These structural checks do not establish test results, UI quality, or semantic acceptance.

## Endpoint replacement

The scheduling caller may replace an agent after repeated failures, a lost or unusable session, exhausted context, or another concrete condition that makes continuation impractical. This is authorized recovery of the same assigned role and needs no additional user confirmation; record and briefly report the reason.

- Give the new agent a self-contained, sanitized handoff: objective and acceptance criteria; source/workspace and constraints; completed work and artifact paths; decisions already made; failures and attempted recovery; remaining work; and uncertain execution or delivery. Transfer only inputs permitted for that role, preserving review independence.
- Confirm the old operation has ended or is fenced before a replacement writes to its workspace. Reconcile uncertain side effects before replaying them; `DELIVERY_UNKNOWN` alone does not authorize duplicate execution.
- Use a fresh `task_id`, preserving the old binding. Dispatch with `start` and the context packet as its prompt. For an authorized replacement that must continue an exact dirty workspace, the [legacy handoff command](references/protocol.md#legacy-handoff-command) retains snapshot validation; it does not select a named pipeline. Record old/new task and endpoint identities, `replacement_for`, reason, and context artifact in the caller's run manifest or task recovery record outside the repository. For a provenance-bound run, register the replacement source with `run-add --nodes-file` and pass `start --run-id`; the operation preserves that declared lineage. Refresh supervision and observer selection after dispatch.
- Preserve provider, model, effort, source/workspace contract, permissions, task scope, and role unless a change is separately authorized. Recheck artifacts and role independence against the new identity. Replacement occupies the existing workflow node and retains its progress and retry/convergence bounds. Where no recovery bound exists, set a finite attempt bound before dispatch; stop and report unresolved work when it is exhausted.
- Qualifying Claude `RESULT_INVALID` retries use `retry-invalid` and its shared budget below. Its replacement replays the original authorized prompt; include the context a fresh session needs when authoring that prompt. A new session never resets the logical operation's retry budget.

## Claude `RESULT_INVALID` retry

The user authorizes a scripted retry policy: any `claude-cli` operation whose terminal error code is `RESULT_INVALID`, whatever its message, may be retried, across every Claude Code role. The control plane still terminalizes that operation and still emits no `safe_recovery`; consume the retry with the dedicated command `retry-invalid --task-id <id> --operation-id <failed-id>`, which owns the persistent three-retry budget, the fingerprint comparison, the new-session replacement trigger, and the lineage record — do not keep a second manual ledger for them. [The retry-invalid contract](references/protocol.md#scripted-claude-result_invalid-retry) is the source of truth for the persisted semantics: budget accounting, fingerprint rules, replacement conditions, contract reapplication, and `parallel_role` continuity.

This budget is separate from any semantic round or convergence bound and never extends one. A replacement session changes endpoint identity: disclose it in `Pipeline Check` and re-evaluate every identity-continuity and role-independence check against the new endpoint, which may no longer satisfy them.

## Workspace and parallel-write policy

- Create task-required worktrees and their isolated local branches for any authorized task without additional user confirmation. Choose distinct temporary branch names when needed. This authorization covers isolation only; endpoint replacement follows its own policy above, while workflow expansion, external writes, and source exceptions require their own authority.
- `reuse-or-create`: reuse the one clean source-branch worktree or create it; writable operations hold exclusive workspace and branch leases until the provider operation ends.
- `isolated`: use a distinct explicit `--workspace-branch` for each concurrent CLI task, including bypass reviews; create or reuse its worktree from the fixed source head. Continue later rounds in that same task's workspace.
- `shared-readonly` and `--read-only` remain low-level compatibility capabilities; do not select them for new Skill dispatches. A strict review prompt cannot satisfy the runtime's read-only requirement for a shared lease.
- Same-MR parallel editing with integrated commits requires caller-declared `--parallel-group`, worker order, one integrator task id, and the original MR source branch as `--integration-target-branch`. Workers use `isolated`; the integrator uses `reuse-or-create` and lists successful worker task ids in order. Concurrent reviews use isolated worktrees without integration metadata or an integrator.
- The caller starts the named integrator only after the workers are terminal. Agent Lord validates the declared barrier and isolation contract; it does not invent workers, an integrator, merge order, or another MR.
- For declared parallel editing, a missing or inconsistent integration plan returns `NEEDS_DECISION`. Read [declared same-MR parallel writes](references/protocol.md#declared-same-mr-parallel-writes) before dispatching concurrent writable tasks.

## Waiting and reporting

For ordinary multi-endpoint work, register all authorized nodes, including pending ones, before dispatch with `run-create --nodes-file ...`; start each with `--run-id ...`. Each node records its role and exact user request, named pipeline, or existing-role replacement source. A self-authored manifest is not authority. Follow [node provenance and reporting](references/scheduling-updates.md); durable `plan-*` runs keep their own documented role contract. Add assignments with `run-add --nodes-file ...` and supervise with `checkpoint --run-id ... --include-response`. Checkpoint output carries only a compact per-task `node` summary — `{ role, source: { kind, reference?, task_id? } }`, with `reference` kept only for pipeline sources; read full provenance from `run-status` or the persisted records. After receiving and processing each terminal result, acknowledge its returned receipt with `run-ack`. An acknowledgement means the caller received that result, not that its content passed review. Membership persists across caller restarts; the runtime still neither dispatches tasks nor chooses their implementation. Keep the existing retained controller-handle cleanup and recovery responsibilities.

`checkpoint` wakes the caller for terminal or model-actionable state before its default 120-second quiet deadline. `CHECKPOINT_QUIET` with exit `124` means this wait returned without an actionable result; it is neither a provider failure nor evidence of error-free execution. Continue with the remaining active task selection. An automatic selection with no active task returns quiet immediately; stop that empty loop and reconcile any expected task. Read [the supervision reference](references/supervision.md) for multi-task selection, compact output, and recovery supervision semantics.

- Choose a bounded quiet window that fits the host; for long-running tasks with a live observer, `checkpoint --seconds 600 --include-response` reduces repeated quiet returns while the runtime continues its normal supervision and wakes early for actionable state. Honor an explicit user interval. The default remains 120 seconds. Select a registered set with `--run-id`. Without a set, put each id in exactly one selection: `--task-id` for a task whose record is confirmed present; `--starting-task-id` for a just-dispatched task whose record may not exist yet. Different ids may use different flags in the same command. A starting selection continues supervising the task after its record appears; it needs no duplicate `--task-id`. An unknown `--task-id` still fails. Read `starting[]` on return: `not_observed` means only that no record was seen in the window, so use the dispatch command's own exit status and error envelope to decide whether the dispatch actually failed.
- Keep at most one outstanding checkpoint per selected task set, and put every active task in exactly one selection — never in two concurrent checkpoints. Selections that share no task, such as independent runs, may each hold their own concurrent checkpoint and acknowledge their own results with `run-ack`. If the host tool yields a running command handle, resume that handle until completion; start that selection's next checkpoint only after it returns. Preserve the checkpoint's quiet deadline when adapting host-tool wait/yield windows to responsiveness or heartbeat requirements. An unchanged wait does not call for another `check`, log read, or watcher.
- Use `reporting.should_notify` and its structured events to avoid repeating unchanged task status. Continue processing `actionable` even when reporting is suppressed; notification deduplication never acknowledges results or suppresses recovery. Keep tool activity in Observer. Report milestones only with concrete artifact or endpoint evidence; a tool name or event count proves neither stage nor near-completion. `progressing` and `tool_wait` describe event or tool activity, not task health, freedom from blocking, or validation success.
- Keep checkpoint window numbers and quiet-window boundaries internal unless the user asks about them. They divide supervision waits, not execution stages, retries, or endpoint sessions. If higher-priority host instructions require periodic commentary, report only known elapsed time and whether a new result has arrived, for example: "Still waiting on the same MCode task; no final result received." A missing failure report does not establish that no errors occurred. This Skill cannot override the host's cadence.
- At completion, consume the canonical final text once (prefer the inline response) and report the result, artifact location, source SHA when applicable, and actual model/variant or its verification limit. When assessing delay, separate caller preparation, endpoint execution, and result retrieval using available timestamps; identify unmeasured intervals. Shorter polling does not make the endpoint execute faster, and any speedup target remains unverified until measured.

## Provider routing and defaults

- Claude Code is an ordinary execution endpoint and may perform any user-assigned implementation, research, review, test, or other node. This execution role is independent of Fable decision routing.
- `claude-cli`: default to configured `claude-fable-5` / `xhigh`. The active `provider-config` resolution policy keeps Agent Lord defaults independent of Claude user settings; `claude-user-settings` remains available for installations that opt into per-field settings resolution. Freeze both resolved values at `start`.
- Explicit Claude model and effort arguments override independently; unspecified fields follow the configured resolution policy. When both are explicit, both win. The default retry plan permits five attempts. When the explicit or resolved primary model belongs to the Fable family, five failed attempts are followed by up to five configured `claude-opus-5` attempts on the same session; report that fallback as the model that actually ran.
- `codex` or `codex-cli`: use Codex CLI, defaulting to `gpt-6-astra` with `xhigh`. Treat an unqualified user request for “Codex” as this route.
- `mcode` or `mcode-cli`: default to `custom_provider:mafia-claude/claude-opus-5` with `xhigh`. Model and effort override independently. MCode validates an explicit `--effort` against the selected model's live `effortOptions` before sending a request; Agent Lord freezes and reapplies the accepted value on every later turn. A `#variant` remains part of model identity and never substitutes for `--effort`. Terminal metadata verifies the actual model and any requested variant; effort is argument-enforced because MCode's schema-version-1 terminal result does not echo it.
- `codex-app`: use only when the user explicitly requests the App/Desktop endpoint. Existing App task handles remain App tasks.

Explicit user values override defaults. `--retry-attempts` overrides the primary Claude stage; the configured Fable fallback budget remains independent. `config/providers.json` is the executable source of truth for these policies.

## Codex App action handshake

Codex App host tools are model-side tools, so the script emits an action instead of guessing a shell bridge. The model is a transport carrier:

1. Call exactly `action.tool` with `action.arguments`.
2. Preserve the complete raw tool result in a temporary file outside the repository.
3. Run `node core/dist/cli.js accept --action-id <id> --result-file <file>`; add `--auto-read` when you only intend to keep polling the same thread.
4. Continue from the new envelope.

The App adapter's thread identity, route recovery, bounded listing retries, and `host-inherited-unverified` permission recording live in [the App transport seam](references/transports.md#codex-app-transport-seam) and [the execution contract](references/protocol.md#execution-contract).

## Artifacts and compatibility

Successful local CLI turns automatically publish a final-response-only artifact; Codex App reads do the same. `export-artifact` is an auxiliary import path whose strict per-provider verification — operation markers, Claude session binding, the `mcode-stream-json` refusal, and the `EFFORT_UNVERIFIABLE_FORMAT` warning — is specified in [the execution contract](references/protocol.md#execution-contract); a rejected export never invalidates an already-succeeded operation or its artifact.

Version 1 task handles remain readable, but `turn` fails closed because those records did not preserve model, effort, permission, or source. Use `node core/dist/task-store.js upgrade` with explicit values before continuing one; it never infers the missing contract. The compatibility interface also supports explicit registration and cleanup; new work uses `node core/dist/cli.js`.

## Live observer and native-terminal launcher

The observer is a TypeScript/Node service with React and vendored Vercel AI Elements components. Build with `cd observer && pnpm install --frozen-lockfile && pnpm build` when its dependencies or compiled assets are missing or stale. Use `pnpm --dir <agent-lord-root>/observer preview:attach` for HTTP-verified task binding and a focused URL; the host link API only requests display. [Observer instructions](observer/README.md#task-binding-after-dispatch) define reuse and failure handling. The launcher checks authenticated instance identity and PID before stopping a service.

The loopback view combines an explicit task allowlist, journal/native exec projections, snapshot, cursor and SSE. It observes Codex CLI, Claude Code and MCode output; Codex App has state only. It never runs checks, checkpoints, recovery, or prompts. Its only execution-side action is an explicit user click that invokes the constrained `terminal-open` control-plane command for an allow-listed task; no browser-supplied shell text is accepted. This is allowed while an operation is running: the original process continues, while a new prompt in the opened terminal may be rejected or queued by the provider's busy guard. It separates execution status from declared delivery evidence and provides native terminal resume commands when Session identity is available. Private runtime files live under `<state>/observer/`; stopping the observer leaves the tasks running. Read [observer/README.md](observer/README.md) for setup, privacy boundaries, lifecycle commands, and the component provenance/license.
